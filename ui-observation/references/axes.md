# 観察軸リファレンス

「使いにくい」「使いやすい」を分解するための軸。1つの体験が複数の軸にまたがるのが普通。

このファイルが軸の唯一の定義元。SKILL.md や観察メモに軸の定義を複製しない。

**作品名・アプリ名は書かない。** 例を載せるときは「あるモバイルゲーム」のように匿名化する。具体名は観察メモ側に置く。

---

## 1. 情報アクセスのコスト

**問い: 頻繁に参照するものに、毎回どれだけの距離を移動させられるか。**

参照頻度と到達コストが逆相関しているとストレスになる。よく見るものほど近くにあるべき。

悪い例: 電話帳がページの先頭にあるのに、1枚送りでしか移動できず、参照のたびに同じ距離を戻らされる。

Web での対応: 主要導線がハンバーガーメニューの奥深くにある。よく使う機能が設定画面の3階層下にある。

## 2. 認知負荷の外部化

**問い: ユーザーの短期記憶に頼らせていないか。**

UI の仕事のひとつは「覚えなくてよくすること」。参照と入力を同時にできない設計は、この責務を放棄してユーザーの記憶に押し付けている。

悪い例: 電話帳を開いたままにできないため、番号を暗記してから入力画面に移動する必要がある。

Web での対応: 確認画面で入力内容が見えない。長いフォームで前の入力値を参照できない。エラーメッセージが該当フィールドから離れた位置に出る。

## 3. 意図と割り込みの衝突

**問い: ユーザーが行動しようとした瞬間を、システム都合で中断していないか。**

ユーザーには意図がある。それを尊重せず割り込むと、単に待たされる以上の苛立ちが生まれる。特に、割り込みによって直前に構築した状態(暗記した内容など)が壊れると被害が大きい。

悪い例: 電話をかけようとしたタイミングでイベント会話が挟まる。

Web での対応: 操作中に出るモーダル。スクロール中に割り込むポップアップ。入力途中の自動リロード。

## 4. 入力精度

**問い: 入力手段が、要求される精度に適しているか。**

そもそも手段の選択が誤っていることがある。精度が求められる入力に、精度の低い手段を割り当てていないか。

悪い例: 数字の連続入力をアナログスティックで行わせる。

Web での対応: タップ領域が小さすぎる。ドラッグ操作でしか調整できない数値入力。直接入力を許さないスライダー。

## 5. エラー回復コスト

**問い: 失敗したとき、どこまで戻されるか。**

1文字消せば済むはずのものを全消しさせるのは、失敗のペナルティが過大。回復コストが高いほど、ユーザーは操作前に緊張し、失敗時のダメージが大きくなる。

悪い例: 電話番号を誤入力すると最初から入力し直し。

Web での対応: バリデーションエラーでフォーム全体がクリアされる。戻るボタンで入力内容が消える。確認画面から修正に戻れない。

## 6. 操作頻度の重み付け

**問い: その操作を何回するかを織り込んで設計されているか。**

1回あたり3秒の無駄も、毎日繰り返せば膨大な苦痛になる。**頻度は設計の前提を変える。** 1回きりの体験を評価するときには出てこない視点。

良い例: デイリーミッションをボタン1つで自動消化できる。クエストがクエスト単位で止まらず、進めるところまでノンストップで進む。アニメーションの再生条件を「毎回/1日1回/非表示」から選べる。

Web での対応: 毎日使う管理画面で、ログインのたびに同じフィルタを設定し直す。よく使う操作にショートカットがない。

## 7. 質の非対称性

**問い: 表現の質と操作の質を、分けて評価しているか。**

ビジュアル・シナリオ・映像表現が優れているのに、インタラクション設計だけが落ちている作品は多い。これは職能の境界にある問題で、「作れる力」と「操作を設計する力」が別物であることを示す。

評価するときに一緒くたにすると、この重要な非対称性が見えなくなる。分けて評価すること。

観察例: 映像表現・ビジュアル・シナリオは高品質だが、操作性だけが明確に劣る作品。

## 8. 入力手段への適合(移植の可搬性)

**問い: そのプラットフォームの入力特性に合わせて設計されているか。**

**ビジュアルは可搬だが、インタラクションは可搬でない。** 見た目は移植しても劣化しないが、操作は入力手段に強く依存するため、前提が変わると壊れる。

構造的な背景: 開発の主戦場が PC(マウス・キーボード前提)で、コンシューマ版は移植。入力手段が変わったのに UI 構造が据え置かれると破綻する。小規模開発ほどプラットフォーム別の UI 再設計まで手が回らない。

逆に、単一の入力手段のみを前提にできる場合、そこに全力を注げるため完成度が上がりやすい。

Web での対応: デスクトップ用 UI をブレークポイントだけ変えてモバイルに出すと壊れる。タップ領域・片手操作・ホバー非対応といったインタラクションの前提が違うため。

## 9. 省略の許容と補償

**問い: ユーザーが手を抜くことを許しつつ、体験の連続性を保っているか。**

単に省略させるのではなく、省略しても本筋から脱落しないよう補償しているかが分かれ目。省略機能があること自体より、その後のケアが設計の質を示す。

良い例: ストーリーをスキップすると、あらすじが表示される。

Web での対応: オンボーディングをスキップしたあと、必要になった時点で該当機能の説明に辿り着けるか。チュートリアルを飛ばした人がヘルプから同じ情報に到達できるか。

## 10. 時限性の緩和(機会損失への救済)

**問い: ユーザーの意志と無関係な機会損失に、回復の窓を用意しているか。その窓に、追加の学習なしで到達できるか。**

軸9との違いは**逃した理由**にある。9は「ユーザーが自分の意志で飛ばした」ことへの補償。10は「その場にいなかった」ことへの救済で、怠慢でも判断でもなく、単なる不在によって発生する。

機会損失の重さは、次の機会までの間隔で決まる。年1回のものを1日で閉じると、逃した代償が最大化される。

**設計の質は「救済を用意したか」ではなく「たどり着けるか」で決まる。** 猶予期間があっても、専用画面を掘らされたり、救済機能の存在を知る必要があったりすると、名目上の救済に終わる。既存の導線に乗せられているかを見る。

良い例: 誕生日ボイスが当日限定ではなく1週間聞ける。しかも再生は専用画面ではなく、ホーム画面のキャラが喋る既存仕様に相乗りしている(あるモバイルゲーム)。

Web での対応: 期間限定のお知らせを見逃した人が後から同じ情報に到達できるか。通知の代替導線が、専用の通知履歴ではなくユーザーが元から見ている面にあるか。セール終了後に「終わったこと」だけが分かって内容が消える設計になっていないか。

## メタ視点: 欠点の相互作用

**個々の欠点は軽微でも、掛け算で体験が悪化する。**

これを指摘できるかどうかが、単なる欠点の列挙と分析の分かれ目。

構造の例:

認知負荷(暗記を強いられる)→ その状態で入力精度の低い操作を行う → 失敗するとエラー回復コストが最大(全やり直し)→ さらに割り込みによって暗記内容が飛ぶ

個別には「ちょっと不便」でも、連鎖すると際立った苦痛になる。分析では、この連鎖の順序と増幅の仕方を書く。

## 軸の追加について

軸は固定ではない。既存の軸で説明できない観察が出てきたら、それは新しい軸の候補。無理に既存の軸に押し込めず、ユーザーに提示して軸の追加を相談すること。

**良い例(うまくできている設計)は軸が見つかりにくい。** 悪い例は不満として言語化されやすいが、良い設計は「摩擦がないこと」として現れるため自然すぎて気づかない。良い例を扱うときは、より慎重に掘る。

軸を追加するときは、**既存の軸との差分がどこにあるかを明示する。** 軸9と軸10が「逃した理由(意志か不在か)」で分かれているように、境界を言語化できて初めて独立した軸になる。似ているだけなら既存軸のサブタイプとして扱う。

追加は必ずこのファイルへの編集として行う。会話の中で合意しただけでは追加されていない。
