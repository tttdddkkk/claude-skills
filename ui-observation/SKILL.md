# UI Observation

体験した UI について、断片的な気づきを構造化し、あとで記事にまとめられる形の観察メモとして蓄積する。

## このスキルの前提

**入力は雑でいい。** 「あのゲームのメニューがイラッとした」程度で成立する。整理してから投げようとすると腰が重くなって続かないので、雑に投げられることが設計上の要件。

**いきなり完成品を出さない。** 観察には言語化されていない部分が必ずある。対話で掘ってから構造化する。

**溜めることが目的。** 1回の出力は「観察メモ」であって記事ではない。メモが溜まってから記事にする。

## 軸の扱い(重要)

観察軸の一覧・定義・個数は `references/axes.md` だけが持つ。**このファイルには軸を書かない。**

同じ内容を複数の場所に置くと必ず食い違う。軸に触れる前に `references/axes.md` を読むこと。「今いくつあるか」もそこで数える。

軸を追加・更新するときは `references/axes.md` を編集する。会話の中だけで合意して終わらせない。ファイルに入っていない軸は存在しない。

## 保存先

観察メモは、公開しない別リポジトリの `notes/` に置く。

**カレントディレクトリがそのリポジトリでない場合は、書き込む前に保存先を確認する。** パスを推測して書かない。

### 固有名の扱い

**作品名・アプリ名・サービス名は観察メモにだけ書く。** 軸の定義(`references/axes.md`)には書かない。

軸は一般化された原則であり、特定の製品への言及を含めると、公開できる範囲が製品名に引きずられる。軸に例を載せるときは「あるモバイルゲーム」「ある予約サービス」のように匿名化し、具体名が必要な記述は観察メモ側に置く。

## ワークフロー

### 1. 受け取る

ユーザーが体験について語ったら、まず評価軸に当てはめずに聞く。先に枠を当てると、ユーザー自身の観察の質感が失われる。

### 2. 掘る

**質問は一度に1つまで。** ユーザーが答えなければそこで切り上げてよい。掘る目的は、ユーザーが無意識に使っている評価軸を表に出すこと。

掘る観点の例:

- その操作は何回くらい発生したか(頻度は設計評価を大きく変える)
- そのとき何を期待していたか(期待と実際のズレが問題の本体であることが多い)
- 他の部分(ビジュアル、シナリオ、機能)の出来はどうだったか(質の非対称性は分析の核になりやすい)
- 他のプラットフォーム版や類似製品ではどうだったか

ユーザーが自分から付け足した情報は、たいてい分析の核になる。軽く流さない。

### 3. 軸に分解する

`references/axes.md` を読み、「使いにくい」がどの軸に該当するか分解する。1つの体験が複数の軸にまたがるのが普通。

### 4. 相互作用を見る

**個々の欠点は軽微でも、掛け算で体験が悪化する。** これを指摘できるかどうかが、単なる欠点の列挙と分析の分かれ目。連鎖の順序と、どこで増幅されたかを書く。

### 5. 一般化する

その観察が他の文脈にも当てはまる原則かどうかを検討する。ゲームUIの観察が Web フロントエンドの設計原則に翻訳できると、メモの価値が大きく上がる。

### 6. メモとして保存する

`templates/observation.md` の形式で書き、保存先の `notes/` にファイルとして保存する。会話に貼って終わりにしない。

### 7. 軸の見直し

既存の軸で説明できない観察が出てきたら、新しい軸の候補としてユーザーに提示する。無理に既存の軸に押し込めない。

追加を決めたら、その場で `references/axes.md` を編集する。**既存軸との差分(境界)を言語化できて初めて独立した軸になる。** 似ているだけなら既存軸のサブタイプとして扱う。

## 出力スタイル

平易な会話体の日本語散文を基本とする。

- 不要な Markdown 装飾、自己宣伝的なフレーム(「素晴らしい観察ですね」等)を入れない
- ファイルに書くので、本文をコードブロックに入れて渡さない
- ファイル名の案を尋ねない。命名規則から自分で決めて保存し、保存したパスだけ伝える
- ユーザーが自分でモデル回答を提示した場合は、それを起点ではなく**到達点**として扱う。さらに膨らませない
- 専門用語(軸、推し活、メンカラ等)は文脈に応じてそのまま使ってよい

## ファイル命名

観察メモは気づき単位で1ファイル。`YYYY-MM-DD-短いスラッグ.md`。

同じ作品の気づきが後日追加されても、既存ファイルを探して追記しない。新しいメモとして独立させ、フロントマターの `subject` で紐付ける。

## 記事化

メモが溜まったら記事にまとめる。束ね方は2通り。

- **作品単位** — 1作品の複数の気づきを統合する。個別の指摘より、相互作用を語れる分説得力が出る
- **軸単位** — 複数作品を横断して1つの軸を論じる。こちらの方が読み物として強いことが多い

記事化を依頼されたら、`notes/` のフロントマターを走査して該当するメモを集め、`templates/article-draft.md` の形式で下書きを作る。

## やらないこと

- 評価軸を先に押し付けない。ユーザーの観察を軸に当てはめるのであって、軸から観察を導かない
- 一度に大量の質問をしない。1回1問
- 記事の完成品をいきなり作らない。メモが本体
- 憶測で製品情報を補わない。バージョンや仕様が不確かなら、その旨を明示するかユーザーに確認する
- 軸の定義をこのファイルや観察メモに書かない。`references/axes.md` の外に軸を増やさない
- 作品名・アプリ名を `references/axes.md` に書かない
