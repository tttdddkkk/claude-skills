# スキル作成スキル

新しいスキルのSKILL.mdを作る。ヒアリングを先行させず、**まずたたき台を出し、推測した箇所を明示して確認を取る**。空欄だらけの雛形や質問攻めから始めない。

## 0. 作らない方がよい場合を先に判断する

以下に当てはまるならスキル化を提案せず、その旨を伝える。

- 一度きりの作業(スキルは繰り返し使う手順のためのもの)
- 「常にこう振る舞ってほしい」という恒久的な好み → CLAUDE.md の領域
- 「〜したら自動で実行」という自動発火 → hooks の領域(update-config スキル)
- 既存スキルとトリガーが重複する → 既存スキルの更新を提案する

## 1. たたき台を生成する

依頼内容から読み取れる範囲で全セクションを埋める。埋まらない箇所は空欄にせず、**推測で仮の内容を書いた上でマーカーを付ける**。

```
<!-- 推測: 出力先は ~/Documents と仮定。要確認 -->
```

参照できる材料があれば先に読む(過去の会話ログ、対象ディレクトリの構成、既存スキルの書き方など)。推測の材料が無い箇所ほど、後の確認で優先的に聞く。

## 2. SKILL.md の必須構成

以下は**全スキル必須**。1つでも欠けたたたき台を提示しない。

| セクション | 内容 |
|---|---|
| frontmatter | `name`(kebab-case、ディレクトリ名と一致) / `description` |
| 冒頭の要約 | 1〜3行。このスキルが何をするか |
| 手順 | 番号付き。実行可能な単位に分ける |
| **禁止事項** | やってはいけないこと。「〜しない」と断定形で書く |
| **出力形式** | 成果物の形式・保存先・ユーザーへの提示方法 |

### description の書き方

descriptionは**発動条件を決める唯一の材料**。次の3点を必ず含める。

1. **何をするか** — 動詞で始める短い説明
2. **いつ発動するか** — ユーザーが実際に言いそうな表現を具体的に2〜4個。抽象的な分類語ではなく生の言い回しを使う
3. **いつ使わないか** — 紛らわしい隣接スキル/機能があれば、その名前を挙げて除外する

```
✗ 悪い例: 「ドキュメント関連の作業を支援する」
   → 何をするのか、いつ発動するのか判断できない

✓ 良い例: 「議事録Markdownを整形して要約を追記する。
   「議事録をまとめて」「この打ち合わせメモを整えて」のような依頼で使う。
   新規に議事録を書き起こす場合には使わない。」
```

### 禁止事項の書き方

「注意する」「なるべく避ける」ではなく、判定可能な形で書く。特に以下は該当すれば必ず入れる。

- 無断で上書き・削除してはいけないファイル
- 確認なしに実行してはいけない操作(外部通信・課金・破壊的コマンド)
- 勝手に補完・修正してはいけない対象(ユーザーの原稿、設定値など)

### 出力形式の書き方

- 成果物のファイル形式と命名規則
- 保存先(一時ファイルか、確定ファイルか)
- ユーザーへの提示方法(プレビューするか、パスを伝えるだけか)
- 確定前に確認を取るかどうか

## 3. 推測箇所を提示して確認する

たたき台の本文とは**別に**、推測で埋めた箇所を箇条書きで列挙する。各項目は「何を・何と仮定したか・なぜそう仮定したか」の3点を1行で書く。

```
- 保存先: ~/Documents/reports/ と仮定(依頼文に指定がなかったため)
- 実行頻度: 都度手動と仮定(定期実行の言及がなかったため)
```

選択肢が2〜4個に絞れる項目は AskUserQuestion で聞く。それ以外は箇条書きのまま提示し、回答を待つ。

**確認が取れるまでファイルを保存しない。**

## 4. 保存先を確認して保存する

保存先は**推測で決めない**。次の順で確定させる。

1. 依頼文に指定(「プロジェクトに入れて」「全プロジェクトで使いたい」等)があればそれに従う
2. 指定がなければ、カレントディレクトリがgitリポジトリか確認する
   ```
   git rev-parse --show-toplevel 2>/dev/null
   ```
3. AskUserQuestion で保存先を聞く。判断材料をそのまま選択肢の説明に書く

| 保存先 | パス | 向いているケース |
|---|---|---|
| 個人用 | `~/.claude/skills/<name>/` | どのプロジェクトでも使う汎用の手順。自分専用 |
| プロジェクト用 | `<リポジトリルート>/.claude/skills/<name>/` | そのリポジトリ固有のパス・ツール・規約に依存する手順。gitでチームと共有したい |

- リポジトリ外(手順2が失敗)の場合はプロジェクト用の選択肢を出さず、個人用を提示して確認する
- 判断が付く場合は推奨側を選択肢の先頭に置き、理由を1行添える
- 保存先に同名ディレクトリが既にある場合は**上書きせず中断**し、既存の内容と衝突点をユーザーに報告してから指示を仰ぐ

確定したパスに `SKILL.md` を保存する。補助ファイルが必要な場合のみ同ディレクトリに置く(`scripts/`, `references/`, `templates/` など)。SKILL.md 1枚で足りるなら増やさない。

保存後、保存先のパスと、スキルを認識させるために必要な操作があればそれを伝える。

## 禁止事項

- 空欄・プレースホルダだらけのSKILL.mdを「たたき台」として提示しない。全セクションを推測で埋めてから出す
- 推測した箇所を黙って確定しない。必ずマーカーと箇条書きの両方で明示する
- 確認前にファイルを保存しない
- 保存先を推測で決めない。個人用かプロジェクト用かは必ず確認を取る
- 保存先に既存の同名スキルがある場合、確認なしに上書きしない
- 禁止事項・出力形式のセクションを省略しない。「特になし」と書かせるのではなく、依頼内容から具体的な項目を推測して埋める
- descriptionを抽象語だけで書かない(「〜を支援する」「〜関連の作業」)
- 使われるか分からない機能を先回りして手順に足さない
- 他のスキルやCLAUDE.md、settings.json を、依頼されていないのに書き換えない

## 出力形式

1. **たたき台本文** — SKILL.md 全文をコードブロックで提示(この時点では未保存)
2. **推測箇所の一覧** — たたき台とは別に箇条書き。各行「項目: 仮定した内容(そう仮定した理由)」
3. **確認の依頼** — 保存先(個人用/プロジェクト用)は必ず AskUserQuestion で聞く。その他の推測箇所も、選択肢が2〜4個に絞れるものは同じ質問にまとめる

確定後の保存時は、保存したパスと、次に何をすればスキルが使えるようになるかを1〜2行で伝える。
