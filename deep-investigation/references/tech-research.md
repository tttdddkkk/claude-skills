# 技術調査・選定

## 一次 / 二次の分類

`[確認]` に昇格できるのは一次ソースのみ。二次しかない場合は `[推定]` とし、根拠に `(二次)` を明示してURLを残す。

| 一次 | 二次 |
|---|---|
| **自分で実行した結果**（最上位） | 技術記事・解説ブログ |
| インストール済みの実装コード・型定義 | まとめ記事・比較記事 |
| 公式ドキュメント（バージョン一致時） | Q&Aサイトの回答 |
| CHANGELOG / リリースノート | 第三者による要約 |
| Issue / PR 内のメンテナ発言 | モデルの記憶 |
| RFC・W3C・TC39 等の仕様書本体 | |
| 企業の公式発表 | |

**媒体ではなく、その主張に対して一次かで決める。**

- 個人ブログでも、自分で測ったベンチマーク値は、その数値については一次。ただし「Aの方が速い」という一般的主張の根拠には二次
- 公式docsでも、対象バージョンが自分の環境と違えば、自分の環境については二次以下
- メンテナの「次で直す予定」は、*予定がある*ことには一次。*今どう動くか*の根拠にはならない

いずれも「質が中くらいの出典」ではなく、**その主張についてはスコープ外**。中間評価で塗りつぶさず、主張の側を、その出典で言える範囲に狭める。

## 二次から一次へ渡る

記事は**一次への導線として使う**。記事で当たりをつけ、そこに挙がっている型定義・docs・Issue を自分で確認し、出典にはそちらを書く。

型定義を読めば `[確認]` にできる場面で、記事を読んで `[推定]` に留めるのは純粋な損失。`node_modules` に入っているものは、まずそれを読む。

## URLの扱い

規則そのものは SKILL.md「URLは取得したものしか書かない」に従う。技術調査で特に効く2点だけ補う。

- URLには**取得日と対象バージョン**を必ず添える。技術情報は静かに腐るため、日付のない引用は数ヶ月後に検証不能になる
- Issue / PR 番号の捏造は、番号だけ見ると本物に見えるため発覚が遅れる。番号は必ず取得済みのページから写す

## 「できない」の検証

「Xはできない」は最も間違えやすい主張。次のどれかに到達していなければ `[未確認]` にする。

- 公式ドキュメントに制約として明示されている
- Issue でメンテナが否定している / `wontfix` で閉じている
- 型定義・実装を読んで、該当APIが存在しない
- 実際に試して失敗した（エラー内容を記録）

**「検索して見つからなかった」は「できない」の根拠にならない。**

## 技術選定の報告

選定では、結論より**判断軸のほうが寿命が長い**。軸を先に出す。

SKILL.md のテンプレートを置き換えるのではなく、`## 結論` の位置に次の節を差し込む。`## 根拠` `## 退けた可能性` `## リスク・未確認` はそのまま残す（技術選定はL規模なので省略できない）。

```markdown
## 判断軸（重み順）
1. 〜（必須 / 重視 / あれば良い）
2. 〜

## 比較
| 軸 | A | B |
|---|---|---|
| 〜 | [確認] 〜 [a1] | [推定] 〜 [b1] |

出典:
- [a1] `node_modules/a/index.d.ts:88`
- [b1] (二次) https://... (2026-08-04 / v5.2)

## 推奨と理由
（3行以内。判断であって事実ではないのでラベルは付けない。根拠は比較表の行を指す）

## 覆る条件
（何が変われば結論が変わるか）
```

セルに出典を書ききれないため、表の直後に脚注で `file:line` / 実行コマンド / URL を列挙する。表だけでは `[確認]` の出典要件を満たさない。

「覆る条件」は必ず書く。状況が変わったときに再調査の要否を判断でき、ADRに転記する際もそのまま使える。

判断軸がユーザーから示されていない場合、**憶測で設定せず Phase 0 で質問する**。軸が違えば結論が変わるため、これは調査を進められない類の不明点にあたる。

## 見落としやすい評価軸

機能比較に寄りがちなので、意識的に確認する。

- **メンテナンス状況** — 直近のコミット頻度、Issueの滞留、メンテナ人数（1人依存か）
- **移行コストと出口** — やめる場合のコスト。ロックインの深さ
- **バンドルサイズ** — 実測が `[確認]`。bundlephobia 等の第三者計測は `(二次)`
- **型の質** — 型定義が実装に追従しているか、`any` の混入
- **既存スタックとの相性** — 依存の重複、ビルドツールとの整合
- **チームの習熟** — 学習コストは技術的優位を打ち消しうる
- **ライセンス** — 再ライセンス事例があるため、現行ライセンスを一次で確認する

## 一次情報に到達できなかった場合

到達できないこと自体を報告する。「調べたがわからなかった」は有用な成果であり、隠すと読み手が同じ調査を繰り返す。

- 何を探したか（検索語・参照先）
- どこで行き止まったか
- 確定させるには何が必要か（試作、実測、問い合わせ）
