# コードベース調査

## 事実収集の5方向

1つの検索で満足しない。ある要素を調べるとき、次の5方向を意識的に埋める。埋まっていない方向がある状態で仮説に進まない。

| 方向 | 得られるもの |
|---|---|
| **定義** | 実際の型・シグネチャ・デフォルト値 |
| **呼び出し元** | 実際にどう使われているか（想定と乖離しがち） |
| **テスト** | 意図された仕様。コメントより信頼できる |
| **履歴** | なぜそうなったか |
| **周辺** | 同じディレクトリの類似実装。慣習が読める |

履歴は特に効く。「なぜこの実装なのか」に対して、コードだけを読んで出した答えは `[推定]` にしかならない。コミットメッセージやPRの説明は `[確認]` になり得る。

```bash
git log -S "検索文字列" --oneline    # その文字列が増減したコミット
git log -L 40,60:path/to/file.ts     # 特定行の変更履歴
git blame -L 40,60 path/to/file.ts
```

## 出典は file:line

ファイル名だけの出典は `[確認]` として不十分。行番号まで書く。読み手が同じ箇所を開けなければ、検証可能とは言えない。

実行結果を根拠にする場合は、コマンドと出力の該当箇所を書く。「テストが通った」ではなく、何を実行して何が出たかを書く。

## 静的検索で見落とすもの

grep やIDEの参照検索は次を拾わない。影響範囲調査では個別に確認し、確認していないなら `[未確認]` として明示する。

- 文字列キーによる参照（`t('key.name')`、`data-testid`、CSSクラス名、ルート定義）
- 動的import・遅延ロード
- DIコンテナ、プラグイン登録、ファイル名規約によるルーティング
- 設定ファイル・環境変数からの分岐
- 型のみの参照（実行時には消えるが、ビルドは壊れる）
- 生成コード（OpenAPI、GraphQL codegen など。生成元を直す必要がある）
- リフレクション的アクセス（`obj[key]`）

## 影響範囲は壊れ方で分ける

「壊れる」には段階がある。混ぜずに分けると、読み手が優先度をつけられる。

| 段階 | 重要度 |
|---|---|
| 1. ビルドが通らない（型エラー、import解決不能） | 無印。CIで必ず止まる |
| 2. 実行時に落ちる（undefined参照、契約違反） | 無印〜`[!]` |
| 3. **静かに挙動が変わる**（デフォルト値、副作用順序、キャッシュキー） | `[!]` |
| 4. 見た目だけ変わる | 無印〜`[-]` |

3が最も見落とされ、最も事故になる。静的解析では出ないため意識的に探す。`[!]` の判定基準「静かに壊れる」に直接該当する。

データの不整合や消失につながる経路が見つかった場合も、段階に関係なく `[!]`。

## フロントエンド特有の観点

- **状態の所有者**: どのコンポーネント／ストアが真実の源か。同じ値が複数箇所で持たれていないか
- **effectの依存**: 依存配列に入っていない参照は、更新されない不具合の温床
- **再レンダリング境界**: memo / context の分割位置。パフォーマンス調査ではここから
- **キャッシュ層**: TanStack Query 等のキャッシュキー設計。キー設計のズレは「更新されない」バグに直結する
- **SSR/CSRの境界**: `window` 参照、hydration mismatch
- **デザイントークン**: 直値が混ざっていないか。デザインとの乖離調査ではまずこれ

## 再現の扱い

不具合調査では、**再現できたかどうか**を必ず報告に書く。

- 再現できた → 再現手順を書く。最も価値の高い成果物になる
- 再現できなかった → `[未確認]`。試した条件と、再現に必要そうな条件を書く

再現していない原因特定は、どれだけコードを読んでいても `[推定]` にとどまる。ここを `[確認]` に格上げしない。

## 質問すべきか、調べるべきか

コードベース調査では、ほとんどの不明点は**自分で調べられる**。「この関数はどこで使われていますか」は聞かずに調べる。

質問に回すのは、コードから導けないものだけ。

- どちらが期待される挙動か（バグ調査で、現状と仕様のどちらが正か）
- 調査対象の境界（どのパッケージ／どのブランチまで見るか）
- 社内固有の用語・機能名が指すもの
- 既知の制約や、触ってはいけない箇所
