# レビュー観点（人間向け）

AIが生成した大量のコードを全部読むより、**コメントに絞ってレビューする方がROIが高い**。

理由:

- lint は形式しか見ない、テストは挙動しか見ない、監視は障害しか見ない。コメントは検出手段が人のレビューしか残っていない
- AIが書いたコメントは、**AIがそのコードをどう理解したかの要約**。コードを1行ずつ追わなくても、コメントを読めばAIの解釈のズレが見える
- 中身は自然言語なので、ドメイン知識がなくても大部分は判定できる
- 観点が抽象的で汎用的なので、プロジェクトをまたいで使い回せる

ただしこれは**コードレビューの代替ではなく優先順位づけ**。限られたレビュー時間をまずコメントに投下するという位置づけ。

## チェックリスト

コメント1つずつに対して、上から順に確認する。

1. **必要性**: このコメントを消しても、コードから同じ情報を読み取れないか？ 読み取れるなら削除
2. **表現の置き換え**: 命名・型・テスト・定数化で表現できないか？ できるならそちらに移す
3. **根拠**: 書かれている内容の出典は何か？ 答えられないなら削除、または確認してから書き直す
4. **事実性**: コメントの内容は、現在のコードの挙動と一致しているか？
5. **上位ソースとの整合**: 設計書・Figmaと矛盾していないか？ 矛盾していれば上位ソースを正として修正
6. **主観・推測表現の検出**: 「おそらく」「〜と思われる」「わかりやすく」「最適化のため」などが含まれていないか？
7. **鮮度**: 今回変更したコードの周辺にある既存コメントは、変更後も正しいか？（**最も漏れやすい**）
8. **寿命**: 一時的な状況・経緯・担当者名など、いずれ嘘になる情報を含んでいないか？

AI駆動開発で特に重要なのは **3・6・7**。
AIは根拠なく断定調で書くことが多いため、6の表現チェックだけでは足りず、3の「出典を言えるか」まで問う必要がある。

## ドメイン知識の要否

| 観点 | ドメイン知識 |
|---|---|
| 1. 必要性 | 不要 |
| 2. 表現の置き換え | 不要 |
| 3. 根拠 | 不要（「出典は？」と聞くだけ） |
| 6. 主観・推測表現 | 不要 |
| 7. 鮮度 | 不要（差分の周辺を見るだけ） |
| 8. 寿命 | 不要 |
| 4. 事実性 | 一部必要 |
| 5. 上位ソースとの整合 | **必要** |

ドメイン知識がなくても**問題の大半は見つけられる**。
残りも「根拠は？」と聞くことで、知っている人に確認を回せる。

この性質により、ジュニアでもシニアのコードに対して対等にレビューできる。
観点が明確なので、指摘する側も受ける側も角が立ちにくい。
スキル差に依存せずチーム全体の品質を底上げできる。

## PRテンプレート用

```markdown
## コメント精査
- [ ] `comment-lint` が error なしで通っている
- [ ] 追加・変更したコメントすべてについて、出典を答えられる
- [ ] 変更したコードの**周辺の既存コメント**が、変更後も正しいことを確認した
- [ ] 推測・感想で書いたコメントが残っていない
- [ ] 仕様・デザイン・業務ルールに関する記述には引用元（チケット／Figma node-id／URL）を付けた
- [ ] TODO にはすべてチケット番号が付いている
```

## 実行順序

1. **人間がコメントを読む** — 勘違いがあればすぐ直せる（最も安く速い）
2. **コメントと実装の一致を検証する** — 1で確定したコメントが検証基準として使える
3. **全体コードレビュー** — 意図と実装のズレが解消された状態から始まるので、ロジック・設計に集中できる

前の工程の結果が、次の工程の精度を上げる構造になっている。
1で人間がコメントを直すと、コメントが「AIの推測」から「人間が承認した意図」に変わり、
負債だったコメントが仕様として使える検証基準に転化する。

## この問題が放置されやすい理由

コメント起因の手戻りが起きても、振り返りでは「AIの精度が低かった」「指示が曖昧だった」で片付けられる。
実際はコメントに引っ張られていても、そこまで遡る人はほとんどいない。
障害として顕在化しないため、原因が特定されず対策も打たれない。

チームに広める際は、**AIが嘘コメントに従って実装した実例を1〜2件、Before/Afterで見せる**と説得力が上がる。
問題が見えにくいタイプなので、可視化された具体例が最も効く。
