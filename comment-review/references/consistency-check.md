# コメント・実装 一致検証（層B）

## 目的

コード内コメントを「正しい説明」ではなく「検証すべき主張」として扱い、実装・上位ソース（設計書・Figma・チケット）と突き合わせる。

**報告だけを行う。コメントもコードも修正しない。** どちらが正しいかは人間が判断する。

## 前提となる信頼順位

1. 設計書・Figma・チケット（上位ソース）
2. 人間が確認済みのコメント
3. 実装
4. 未確認のコメント

- 未確認のコメントを根拠に「実装が誤り」と判定してはいけない
- 上位ソースが手元にない場合は、推測で補わず「判断不能」とする

## 入力

- **対象範囲**: 指定がなければ `git diff`（ステージ済み＋未ステージ）で変更されたファイル
- **確認済みマーカー**: 人間が確認したコメントを識別する方法
  - 指定があればそれに従う（例: 「今回の差分のコメントは全て確認済み」「`// ✓` 付きは確認済み」）
  - 指定がなければ、全コメントを未確認として扱う
- **上位ソース**: ユーザーが提示した設計書・Figma・チケットのパスやURL

入力が足りず判定の精度が大きく落ちる場合は、作業を始める前にユーザーに確認する。

## 手順

### 1. コメントの抽出

対象範囲から以下を抽出する。

- 追加・変更されたコメント
- **変更されたコードの周辺にある既存コメント**（同じ関数・ブロック内。コード変更で嘘になりやすいため必ず含める）
- JSDoc / TSDoc、型定義内のコメント
- TODO / FIXME / NOTE / ASSUMPTION などのタグ付きコメント

対象外:

- ライセンスヘッダ、自動生成ファイル
- lint / 型チェックの抑制ディレクティブ（ただし抑制理由の説明文は対象）

### 2. 各コメントの検証

コメント1件ごとに、以下を確認する。

1. **主張の特定**: このコメントは何を主張しているか（挙動・理由・制約・前提・参照先）を1文で言い換える
2. **実装との照合**: 主張が現在の実装の挙動と一致するか。呼び出し元・呼び出し先まで必要な範囲で追う
3. **上位ソースとの照合**: 上位ソースがあれば、主張がそれと矛盾しないか
4. **根拠の有無**: 出典（チケット番号、仕様書の節、Figmaのnode-id、実測）が書かれているか、または実装・上位ソースから裏付けられるか
5. **推測・主観表現**: 「おそらく」「〜と思われる」「わかりやすく」「最適化のため」などを含むか
6. **必要性**: コードから同じ情報を読み取れるか（Whatの言い換え、変更履歴、設計書の書き写しではないか）

層Aのlintで機械的に判定できる項目（5の表現検出など）は、重複して詳細に指摘しない。
このスキルの価値は **2・3の意味的な照合** にある。

### 3. コメント不足の検出

コメントが**ない**箇所のうち、以下に該当するものを拾う。

- 一見不要・冗長に見えるが意図的と思われる処理（debounce、二重チェック、待機、順序依存など）
- マジックナンバー、ハードコードされた値
- プラットフォーム・ブラウザ・WebView固有の回避策
- 上位ソースに記載された制約を実装しているが、コード上でその理由がわからない箇所

意図が推測できても、**推測した理由を書いてはいけない**。「理由の記載が必要」とだけ報告する。

## 分類

各指摘を以下のいずれか1つに分類する。

| 分類 | 条件 |
|---|---|
| コメント誤り | 実装または上位ソースが正しく、コメントがそれと矛盾している |
| 実装誤り | 確認済みコメントまたは上位ソースが正しく、実装がそれと矛盾している |
| 判断不能 | 矛盾はあるが、どちらが正しいか決める根拠が手元にない |
| 根拠不明 | 矛盾は見つからないが、主張の出典を示せない |
| 不要 | コードから読み取れる内容、変更履歴、設計書の書き写し |
| コメント不足 | 理由の記載が必要なのにコメントがない |

- 未確認コメントと実装が矛盾し、上位ソースがない場合は「判断不能」とする（「実装誤り」にしない）
- 問題がないコメントは報告しない

## 出力形式

```markdown
# コメント・実装 一致検証レポート

対象: <対象範囲>
確認済みコメントの扱い: <指定内容 / 指定なし（全件未確認）>
参照した上位ソース: <一覧 / なし>

## サマリー
- 実装誤り: N件
- コメント誤り: N件
- 判断不能: N件
- 根拠不明: N件
- コメント不足: N件
- 不要: N件

## 指摘

### [分類] <ファイルパス>:<行番号>
- コメント: `<コメント本文>`
- 主張: <1文での言い換え>
- 実際: <実装の挙動、または上位ソースの記載>
- 根拠: <判定の根拠となるコード箇所・ドキュメント>
- 人間に確認してほしいこと: <判断に必要な問い>
```

- 指摘は「実装誤り」「コメント誤り」「判断不能」「根拠不明」「コメント不足」「不要」の順に並べる
- 修正案のコードは書かない。書く場合も「人間に確認してほしいこと」の範囲にとどめる

## 禁止事項

- コメント・コードを編集すること
- コメントを正しい前提として実装を評価すること（確認済みのものを除く）
- 推測で意図を補い、それを根拠に分類すること
- ロジックの妥当性、設計、パフォーマンス、命名など、コメントとの一致以外の観点で指摘すること（層Cの役割）

## 層Cへの引き継ぎ

このレポートで意図と実装のズレが解消された後、層C（全体コードレビュー）を実行する。
層Cでは、このレポートで検証済みの内容を重ねて指摘しない。
