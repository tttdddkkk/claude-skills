# 重大度の定義

すべてのルール追加・分類判断はこの軸で決める。
「なんとなく重要そうだから error」という判断をしないために、被害の種類で分ける。

## error = AIが根拠として採用すると、誤った実装を生むもの

被害は**誤誘導**。放置するとマイナスに進む（間違った方向に実装が進み、手戻りが発生する）。

判定の問い: **これをAIが方針・事実として読んだら、間違った方向に進むか？**

| 種類 | 理由 |
|---|---|
| 推測表現 | 根拠がない記述を、AIは事実として採用する |
| 未解決の仮定 | 同上。確認されないまま残り続ける |
| 感想・主観 | 検証不能だが、AIは設計方針として採用しリファクタを同方向に進める |
| 未検証の事実主張 | 「パフォーマンス向上のため」等。測っていないのに測ったかのように読める |
| 変更履歴・経緯 | 次の変更で100%古くなる。嘘になることが確定している |
| 日付・担当者の直書き | 同上 |
| チケット参照のないTODO | いつ嘘になったか追えず、永遠に残る |
| 引用元のない外部由来の主張 | レビュワーが裏取りを強制される（＝実害はコストではなく調査工数） |
| 行番号による参照 | 編集のたびにずれる |
| 秘匿情報 | 別種の実害 |

## warning = 採用されても害はないが、読むコストだけかかるもの

被害は**コスト**。ゼロのまま止まっているだけで、マイナスには進まない。

| 種類 |
|---|
| コメントアウトされたコード |
| 情報量のない飾りコメント |
| What の言い換え |

## 境界の考え方

### 感想 と 未検証の事実主張 は分ける

- **感想**（わかりやすく、シンプルに、きれいに）: 検証不能。真偽が定まらない → **削除させる**
- **未検証の事実主張**（パフォーマンス向上、最適化、メモリ削減）: 測れば真偽が確定する → **書き方を変えさせる**

検出ロジックは同じ（根拠となる数値・チケット参照がない）が、指摘メッセージを分ける。
削除させるべきものと、書き直させるべきものを混同すると、直す側が迷う。

### 結果 と 制約 は分ける

パフォーマンスを理由にする場合、コメントに残す価値があるのは結果ではなく制約。

- 結果（履歴 → 残さない）: `// 最適化により30%高速化`
- 制約（前提 → 残す）: `// 1000件超で描画が破綻するため仮想スクロール必須`

前者は過去の出来事の報告で、その数値が今も有効かは誰にもわからない。
後者は今も成立していて、壊すと困る条件。これがないと次の人が素直な実装に戻してしまう。

### 時制で切る

全コメントに適用できる簡易判定。

- 「〜した」で終わるもの → 履歴 → 消す
- 「〜である」「〜すると壊れる」 → 制約 → 残す

## 設計上の注意

- **error を増やしすぎない**。error が乱発されると `--no-verify` が常用され、仕組みごと死ぬ
- **機械で確信が持てないものは warning に置く**。誤検知の多い error は信用されなくなる
- **AIによる判定（層B）は原則 warning 扱いにする**。LLMは非決定的なので、同じコードで通ったり落ちたりするとコミットが信用されなくなる。ブロックは層Aだけに任せる
