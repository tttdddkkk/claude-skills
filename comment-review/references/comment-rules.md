# 質の良いコメントの定義

一言でいうと、**コードからは読み取れず、かつ根拠を示せる情報だけを書いたコメント**。

## 満たすべき4条件

1. **コードで表現できない情報である**: 変数名・関数名・型・テスト名で表現できるなら、コメントではなくそちらで表現する
2. **根拠がある**: 仕様書・チケット・Figma・外部ドキュメント・実測結果など、出典を示せる
3. **コードと一致している**: 書かれている内容が、今のコードの挙動と矛盾しない
4. **寿命がコードと同じ**: そのコードが存在する間はずっと正しい。一時的な状況や経緯は書かない

## 書いてよい種類

| 種類 | 例 |
|---|---|
| Why（なぜこうしたか） | `// iOS WebViewで100vhがツールバー分ずれるため dvh を使用（参照: bugs.webkit.org/show_bug.cgi?id=141832）` |
| 制約・非自明な前提 | `// APIは最大100件までしか返さない（出典: ABC-1234）` |
| 意図的な「変に見える」実装への警告 | `// 二重送信防止のため意図的にdebounceしている。削除しないこと` |
| 外部参照 | `// 参照: figma.com/design/xxx?node-id=1:23` |
| 期限と担当のあるTODO | `// TODO(ABC-5678): バックエンド対応後にフォールバック削除` |
| リポジトリ内の関連実装 | `// @see formatCurrency` |

## 書いてはいけない種類

| 種類 | 例 | 理由 |
|---|---|---|
| What の言い換え | `// ユーザーを取得する` | コードを読めばわかる |
| 推測の意図 | `// おそらく〇〇のためと思われる` | 根拠がない。AIが事実として採用する |
| 感想 | `// わかりやすくするため分割` | 検証不能。AIが設計方針として採用する |
| 未検証の事実主張 | `// パフォーマンス向上のため` | 測っていない。制約の形で書き直す |
| 変更履歴 | `// 〇〇から変更` | gitの役割。次の変更で古くなる |
| 日付・担当者 | `// 2026/09/18 田中対応` | git blame とチケットの役割 |
| 仕様の二重管理 | 設計書の内容の書き写し | 片方だけ更新されて矛盾する |
| 担当・期限のないTODO | `// TODO: あとで直す` | 永遠に残る。いつ嘘になったか追えない |
| 行番号参照 | `// src/utils/format.ts:123 参照` | 編集のたびにずれる |
| 特定できない参照 | `// 詳細は設計書参照` | 結局レビュワーが探すことになる |

## 引用元の書き方

引用の有無が「検証済みかどうか」のマーカーになる。
引用がないコメントは、AIの憶測か確認済みの事実か区別できず、レビュワーが全部調べる羽目になる。

### 引用が必要な主張

- 仕様・要件に関する記述
- デザイン由来の指定
- 業務ルール（手数料・税率・営業日・締め日など）
- 外部API制約
- 不具合回避（プラットフォーム固有の挙動など）

### 認める記法

機械判定できるよう語彙を固定する。

```
// 出典: ABC-1234
// 参照: figma.com/design/xxx?node-id=1:23
// @see formatCurrency
```

- チケット: `ABC-123` / `#123`
- Figma: **node-id 必須**（ファイルURLだけでは結局画面を探すことになるため引用として機能しない）
- 設計書・外部根拠: 許可ドメインのURL（社内wiki、MDN、caniuse、WebKit bug など）
- 同リポジトリ内: シンボル名で指す（`@see funcName`）。**行番号は書かない**

## なぜ人間向けの規約と基準が違うのか

従来のコメント規約は「読む人の負担」が基準だった。その基準では感想コメントは無害どころか親切とされてきた。

しかしAIが読み手に加わると、AIは根拠の有無を判定せず、書いてあることを方針として採用する。
結果、無害だったものが実害に変わる。**読み手が変わったから基準が変わった**。
