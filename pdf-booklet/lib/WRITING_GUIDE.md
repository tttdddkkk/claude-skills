# 原稿執筆ガイド(改ページ崩れを避けるために)

`lib/engine.py`のページネーションはかなり頑健になったが、それでも「入りきらない大きな要素の直前で空白ができる」問題を完全にはゼロにできない(word processorやDTPソフトでも避けきれない一般的な制約)。原稿の書き方でリスクを減らせる部分をここにまとめる。

## 基本の変換ルール
`## 第n章` `### Qn.` `### コラム:` などの記法は `SKILL.md` の「Markdown自動変換ルール」表を参照。

## 改ページ崩れを避けるための書き方

### 1. 見出しラベルは句点(。)を付けない 【要ユーザー確認】
`**コツ3: 読者別に変換させる**` のように、句点なしで終わる短い太字段落は「見出しラベル」として認識され、直後の要素とセットで改ページ判定される(孤立しにくい)。

一方、`**便利さゆえの罠**: それらしい根拠つきで即答してくれるため…になりがちです。` のように句点で終わる完結した1文は「独立した文」として扱われ、直後の要素とはペアリングされない。これは意図的な区別なので、見出しとして機能させたい短い段落は句点を付けずに書く。

この判定はスキル側では自動修正しない(句点の有無は著者の意図そのものであり、勝手に変えると文章の意味が変わりうるため)。該当しそうな箇所を見つけたら、著者の意図(見出しラベルか、完結した文か)をユーザーに確認してから直す。

### 2. POINT要点整理カードの直前に、短い1文だけの段落を置かない(既知の弱点) 【要ユーザー確認】
```
第n章の本文の最後の段落。
```
の直後に
```
**第n章 この章で覚えること**
- ...
```
が続く構成で、直前の段落が「短い(1〜2行)・句点で終わる完結文」だと、その段落とPOINTカードのペアが実際のChromium描画でJS側の見積もりより早く改ページされ、大きな空白ができることがある(原因未特定・`lib/HTML_CONTRACT.md`参照)。

対策:
- 章末の最後の段落は、できれば3行以上のまとまった文章にする(短い1文で締めない)
- どうしても短い1文で締めたい場合、この形(短い・句点で終わる段落の直後にPOINTカード)を原稿中に見つけたら、`scan_h3_orphans.py`や目視確認で実際に崩れているか確認した上で、対応案(`<!-- page-break -->`の挿入など)をユーザーに提示し、指示を得てから編集する。レイアウト指定のみで文意には影響しない変更であっても、確認は省略しない

### 3. 手動マーカーを恐れずに使う
自動判定で解決しない個別ページは、原稿に直接マーカーを書いて確実に対処する(`HTML_CONTRACT.md`「手動レイアウト調整マーカー」参照)。
```
<!-- page-break -->

### 次の見出し
```
これは「原稿側の一時しのぎ」ではなく正式な記法として扱ってよい。ビルドスクリプト側のバグではなく、組版が本質的に避けきれないケースに対する意図的な指定。

### 4. 長い箇条書き・番号リストは気にしなくてよい
`ul`/`ol`は1ページに収まらない場合、自動で複数ページにまたがって分割される(コードブロックと同様)。無理に短くまとめる必要はない。

### 5. 表・引用(NG/OK)・POINT/HINT/COLUMNカードは分割されない
これらは「カードの見た目が崩れる」ことを避けるため、常に丸ごと1ページに収まるよう改ページされる(=次のページに送られる)。極端に長い表・カードを作ると、それだけで丸々1ページの大半を消費したり、直前ページに大きな空白を作ったりしやすい。目安として1カード = A4の半分以内に収まる分量を意識する。

## ビルド後の確認手順
1. `python3 lib/scan_h3_orphans.py <原稿.md> <PDF>` でh3見出しの孤立を機械チェック
2. 表紙・各章扉・装飾の多いページを画像プレビューで目視確認(`SKILL.md`の手順3を参照)
3. 崩れがあれば、まず「1・2」の書き方を見直す。それでも直らなければ「3」の手動マーカーで個別対応する
